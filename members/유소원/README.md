## 6주차
### 사용한 도구:

Figma : 와이어프레임, 프로토타입
### 효과가 있었던 프롬프트: 
영상 파일을 제공하는 동시에, 영상 속 대화 내용을 별도의 텍스트 스크립트로 작성하여 함께 입력했다. 영상만 제공했을 때보다 AI가 대화 내용을 정확하게 파악할 수 있었으며, 불필요한 재질문과 해석 오류가 줄어들어 결과물을 도출하는 데 걸리는 시간이 단축되었다. 또한 시각 정보와 텍스트 정보를 함께 제공함으로써 영상의 상황과 대화 내용을 종합적으로 분석할 수 있어, 보다 정확하고 직관적인 답변을 얻을 수 있었다.
### 실패한 시도와 배운 점: 
- 영상만 입력했을 때 AI는 화면 속 상황과 시각적 요소는 비교적 잘 해석했지만, 음성으로 전달되는 대화 내용은 충분히 인식하지 못하는 모습을 보였다. 이를 통해 영상 분석과 음성 인식의 정확도가 반드시 동일하지는 않으며, AI가 어려움을 겪는 정보는 별도의 텍스트로 제공하는 것이 효율적이라는 점을 확인했다.
- 대화 내용을 AI 음성 인식 도구 등을 활용해 텍스트로 변환한 뒤 제공하자, 직접 대화 내용을 정리하는 수고를 줄이면서도 분석의 정확도를 높일 수 있었다. 변환된 텍스트에 일부 오타가 있더라도 전체적인 맥락을 파악하는 데 큰 문제가 없었으며, 의미 전달에 지장이 없는 경우 별도의 오타 검수 없이도 충분히 활용할 수 있었다. 따라서 모든 입력 자료를 완벽하게 검토 및 수정하기보다는 핵심 정보가 명확하게 전달되고 이에 따른 답변이 내가 원하는 방향으로 나올 수 있도록 이끄는 것이 더 중요하다는 점을 배웠다.
### 남은 한계:
AI가 답변 과정에서 동일한 내용을 반복하거나, 핵심과 직접적인 관련이 없는 이전 대화까지 끌어와 답변을 길게 작성하는 문제가 남아 있다. 이러한 특성은 필요한 정보를 빠르게 확인하기 어렵게 만들고, 결과물을 실제 보고서나 과제에 활용하기 위해 추가적인 편집 작업을 요구한다. 이를 개선하기 위해서는 프롬프트에서 단순히 수행할 작업을 지시하는 것에 그치지 않고, 답변에 포함할 정보의 범위와 분량, 이전 대화의 활용 기준을 구체적으로 지정해야 한다. 예를 들어 다음과 같은 조건을 추가할 수 있다.
- 정보 범위: 이번에 제공한 영상과 스크립트를 중심으로 분석하고, 이전 대화는 필요한 경우에만 참고한다.
- 답변 분량: **핵심 내용 위주로 작성**하며, 동일한 의미의 문장을 반복하지 않는다.
- 정보 활용 기준: 이전 대화에서 확정된 조건은 유지하되, 현재 작업과 **관련 없는 내용은 포함하지 않는다.**
- 결과물 형식: 효과가 있었던 점, 실패 원인, 개선 방향 등 **지정된 항목**에 따라 간결하게 정리한다.
이러한 방식으로 프롬프트를 구체화하면 AI의 답변 방향을 보다 명확하게 통제할 수 있으며, 불필요한 정보와 반복을 줄여 결과물의 활용도를 높일 수 있을 것으로 보인다.

단순히 내용을 요약하라는 요청과 달리, 구조와 분량에 대한 조건을 함께 제시함으로써 기존 분석의 흐름을 유지하면서 핵심 내용만 추출한 결과물을 얻을 수 있었다. 이를 통해 AI에 작업을 요청할 때는 결과물의 목적뿐 아니라 유지해야 할 요소와 수정해야 할 범위를 명확히 지정하는 것이 중요하다는 점을 확인했다.

### 남은 한계:
현재 채택한 디자인은 캐릭터와 질감 표현이 인상적이고 시각적인 개성이 뚜렷하다는 장점이 있다. 그러나 장식적인 요소가 강조되면서 정보의 가독성이 떨어질 가능성이 있고, 시각적 스타일에 대한 사용자 선호도에 따라 호불호가 갈릴 수 있다는 한계가 있다. 따라서 현재 디자인을 그대로 확정하기보다는 시각적 개성과 사용 편의성 사이의 균형을 검토하는 과정이 필요하다. 정보 위계, 버튼 식별성 등을 점검하고, 불필요한 장식 요소를 줄이거나 크기와 배치를 조정하는 방향을 검토할 예정이다. 또한 메인 화면의 디자인 방향을 개선하고 나면 이를 기준으로 검색·사례 상세·긴급 상황 등 세부 화면을 제작해야 한다. 각 화면에 동일한 디자인 규칙을 적용함으로써 앱 전체의 일관성을 확보하고, 실제 사용 흐름에서도 가독성과 사용성을 유지할 수 있도록 제작할 계획이다.

### 사용한 도구:

### 효과가 있었던 프롬프트:
지난 주차의 이미지 생성 경험을 바탕으로, 레퍼런스에서 참고할 요소와 새롭게 창작할 요소를 명확히 구분하여 지시했다. 구체적으로 톤앤매너, 시각적 스타일, 재질감, 오브젝트의 종류와 개수, 배치 등으로 요소를 나누고, 각 항목에 대해 유지할 부분과 변경할 부분을 구체적으로 명시했다. 이를 통해 AI가 참고 이미지를 그대로 모방하는 문제를 줄이고, 원하는 디자인 방향에 더욱 부합하는 결과물을 얻을 수 있었으며, 이미지 생성 이후 수정 작업을 반복하는 횟수를 약 1~2회 수준으로 줄일 수 있었다. 프롬프트 작성 시 단순히 원하는 결과물을 설명하는 것보다, 유지할 요소와 변경할 요소를 구분하고 각 요소의 우선순위를 명확하게 설정하는 것이 작업 효율을 높이는 데 효과적임을 확인했다.
### 실패한 시도와 배운 점:
사용자가 자신의 주거 문제를 해결하기 위한 사례를 탐색할 때, 원하는 정보를 쉽게 찾을 수 있도록 문제 유형별 분류 카테고리를 구성하고자 했다. 이를 위해 각 카테고리에서 발생할 수 있는 문제 사례를 AI에 조사하도록 요청했다. 그러나 초기 결과물은 ‘싱크대 고장’, ‘가구 파손’, ‘배수관 누수’ 등 문제의 유형이나 현상을 설명하는 데 그쳤다. 실제 사용자가 일상에서 마주하는 상황을 떠올리거나 자신의 문제와 비교하기에는 직관성이 부족하다고 생각해, 이후 프롬프트에 자취생이 실제로 겪을 법한 구체적인 상황과 주변 요소를 중심으로 표현할 것이라는 조건을 추가했다. 그 결과 단순한 고장 명칭보다 사용자의 경험과 상황을 반영한 문구를 도출할 수 있었다. 이 과정을 통해 같은 문제를 다루더라도 어떤 관점에서 정보를 구성하느냐에 따라 결과물의 활용도가 달라진다는 점을 배웠다. 특히 사용자에게 제공되는 카피를 작성할 때는 문제 자체를 나열하기보다, 사용자가 자신의 상황을 쉽게 인식하고 공감할 수 있는 관점에서 표현하도록 이끄는 것이 중요하다는 점을 확인했다.
### 남은 한계:
현재 제작한 세부 화면들을 바탕으로 2차 사용성 테스트(UT)를 위한 프로토타입을 제작할 예정이다. 이를 통해 사용자가 문제 유형을 쉽게 이해하고 원하는 해결 사례를 찾을 수 있는지, 화면 간 이동 과정에서 혼란을 겪지는 않는지 등을 확인하고자 한다.
또한 화면에 적용한 카피가 아직 완전히 다듬어지지 않았다는 한계가 있다. 문구가 사용자의 실제 표현과 일치하는지, 문제 상황을 충분히 직관적으로 전달하는지, 다음 행동을 유도하는 데 효과적인지를 추가로 검토해야 한다. 2차 UT 결과를 바탕으로 이해하기 어렵거나 오해의 소지가 있거나, 사용자에 친절하지 않은 문구를 수정하고, 사용자의 문제 인식부터 해결 행동까지 자연스럽게 연결되는 화면과 문구를 완성하는 것을 향후 개선 목표로 설정했다.

### 효과가 있었던 프롬프트:
이번 주에는 단순히 “LLM 기능을 만들어줘”라고 요청하기보다, 기존 프로젝트에서 유지해야 하는 설정, 팀원별 담당 범위, 분석 판단 순서와 완료 기준을 먼저 제시했다. 다음은 실제 작업 조건을 정리한 요청 예시다.

    기존 main에 구현된 화면과 공통 설정을 먼저 확인하고, 소원의 분석 기능과 서버 영역을 중심으로 작업해줘. 다른 담당자의 화면 이동이나 공통 코드는 임의로 바꾸지 말고, 입력과 결과를 주고받는 함수·상태·취소 방법을 분리해줘.

    사용자 글과 사진으로 문제를 파악하고 저장해뒀다가, 이전 사례에서 적합한 사례가 있으면 ID로 원본을 사용해줘. 적합한 사례가 없고 정보가 충분할 때만 새 해결책을 생성하여 API를 절약하고, 기존 사례가 없다는 이유만으로 분석 실패로 처리하지 마. 문의가 필요한 생성 결과에는 대상별 문의 문장도 작성해줘.

    나는 API를 처음 사용하므로 각 과정은 쉽게 설명하고, 단계별 결과를 확인하면서 진행해줘. 비밀 키는 공개되지 않게 해 주고, 실제로 확인한 결과와 아직 연결하지 않은 항목을 구분해줘.

이처럼 “기존 사례 선택”과 “새 해결책 생성”을 구분하자 AI가 원본 사례를 불필요하게 다시 작성하거나, 사례가 없다는 이유만으로 분석을 실패시키는 방향을 줄일 수 있었다. 또한 같은 글·사진을 기준으로 제공업체를 비교하고, 기존·생성 결과 샘플과 오류 상황을 먼저 정리해 팀원의 화면 연결과 실제 API 구현을 나누어 진행할 수 있었다. 구현 후에도 정상 동작만 묻지 않고 취소·중복·시간 초과·입력 보존·저장 실패의 확인 조건을 제시한 것이 검증에 도움이 되었다.
### 실패한 시도와 배운 점:
- 분석 오류를 모두 같은 `api-error`로 표시하면 OpenAI 요청 거절, 응답 형식 문제, DB 저장 문제를 구분하기 어려웠다. 서버의 실패 단계와 고정된 진단 코드만 남기는 방식으로 보완했고, 실제 `provider-http-401` 발생 시 OpenAI 프로젝트 키가 만료된 것을 확인했다. 이를 통해 “서버가 Live다”, “인터넷에 연결된다”, “유효한 키로 분석이 성공한다”는 서로 다른 확인 단계이며, 키 만료일과 실제 호출 결과까지 점검해야 한다는 점을 배웠다.
- 서버 주소를 브라우저에서 열면 JSON만 표시되었고, Android에서 `127.0.0.1`은 휴대폰 자신을 가리켜 PC 실행 환경과 혼동할 수 있었다. 화면을 제공하는 앱과 분석 요청을 처리하는 서버의 역할을 구분하고, PC·USB·시험 서버에 맞는 공개 연결 설정을 전달했다. 비밀 키를 숨기는 일과 앱이 올바른 서버를 바라보도록 설정하는 일을 각각 확인해야 함을 이해했다.
- AI가 작성한 코드를 바로 완료로 간주하지 않고, 실제 휴대폰에서 사진 첨부·입력 유지·분석·문의 문장 복사를 직접 확인했다. 이 과정에서 연결 오류와 화면 복구 문제를 구분해 점검했고, 문의 문장을 수정한 뒤 화면을 이동해도 내용이 유지되는지까지 검증했다. 자동 검사와 사용자 관점의 실제 조작을 함께 확인하는 것이 중요했다.
- 모든 상황에서 새 답변을 생성하는 대신 기존 사례를 우선 사용하고, 동일 입력의 유효한 답변을 재사용하도록 변경했다. 진행 중인 중복 요청을 합치고 실패 후 자동 분석 재시도를 하지 않는 방식도 적용했다. 비용 절감은 단순히 저렴한 모델을 고르는 것뿐 아니라 불필요한 호출 자체를 줄이는 설계와 연결된다는 점을 배웠다.
- 평가 버튼의 선택과 의견 제출을 한 번에 처리하면 의견 시트를 취소할 때 선택 상태까지 혼동될 수 있었다. 두 동작을 별도 API로 나누고, 재시도 식별값과 선택 순번을 사용해 중복 저장과 늦게 도착한 이전 선택을 처리했다. 저장에 성공한 경우에만 성공 응답을 주도록 정리하면서 화면 상태와 실제 DB 저장 여부를 구분하는 필요성을 확인했다.

### 남은 한계:
- 평가·의견 저장 API와 SQL, 1년(365일) 보관 정책은 PR #42를 통해 main에 병합했지만, 직접 확인한 범위는 코드·검사·연결 안내 준비까지다. 실제 Supabase 테이블·주기 삭제 작업·서버 설정 적용과 예슬 담당 B 화면 연결은 별도로 확인해야 한다. 기존 분석 답변 캐시의 7일 유효기간은 평가·의견의 365일 보관과 구분하여 유지한다.
- 키 교체 후 Render 서버가 정상 기동하고 상태 응답을 반환하는 것은 확인했으나, 이것만으로 실패했던 결로 분석이 최종 성공했다고 판단하지 않았다. 실제 재분석 결과와 운영 환경의 요청·응답을 추가 확인해야 하며, 여러 사용자·기기와 실제 네트워크 환경에서의 동작, 응답 품질과 API 비용도 계속 점검할 필요가 있다.
- 국외 처리 안내는 업체 이름만 나열해서 완성할 수 없었다. 사진·글이 OpenAI로 전달되는 경로와 중계 서버, Supabase 저장·지원·운영 로그를 구분해 정리했으며, 정확한 처리 국가·보관 및 삭제 기간·이용자 고지와 동의 화면은 추가 확인·적용 대상으로 남겼다. 이번에 준비한 기능·문서·자동 검사와 실제 운영 적용이 완료된 범위를 구분해 보고하는 것을 향후에도 유지하고자 한다.

- OpenAI API·Render·Supabase: 미국 지정 분석 요청 확인, 시험 서버 배포, 평가·의견 저장과 동의·신고·삭제 기능의 실제 연결 검증
- Android Studio·Android SDK·ADB·갤럭시 퀀텀 4: 별도 테스트 앱 설치, 휴대폰에서 분석·문의·취소·오프라인 복구 확인, 출시용 서명 키 준비

### 효과가 있었던 프롬프트:
이번 주에는 이미 구현한 분석 기능을 출시 화면과 운영 조건에 맞추는 데 집중했다. 기능을 추가하라는 요청과 함께 사용자가 확인할 결과, 보류할 범위, 실제로 완료했다고 판단할 근거를 구체적으로 제시했다. 다음은 작업 조건을 정리한 예시다.

    최신 main과 출시 화면을 먼저 확인하고 분석 기능을 맞춰줘. 생성 결과의 문제 제목은 가급적 짧은 명사로 작성하고, 문의 초안은 최대 4문장으로 맞춰줘. 준비물은 0단계로 표시하되 총 해결 단계 수에서는 제외하고, 각 준비물에는 해당 제품을 검색한 쿠팡 결과 페이지를 연결해줘.

    공개 출시를 준비하되 OpenAI 월 예산은 10달러, 사용자별 새로운 유료 분석은 한국 시간 기준 하루 5회로 준비해줘. 이미 저장된 동일 답변의 재사용과 신규 유료 호출을 구분하고, 무료 서버 운영을 전제로 남는 한계도 알려줘.

    업체의 공식 문서에서 확인한 내용과 실제 계정에서 확인한 내용을 구분해줘. 확인되지 않은 처리 국가와 로그 보관기간은 추측하지 말고, 코드 준비·시험 서버 적용·최종 앱 확인·스토어 제출을 각각 나누어 보고해줘.

이렇게 요청하자 화면에 보이는 문장과 단계 수뿐 아니라 비용, 저장 권한, 삭제 동작까지 같은 기준으로 확인할 수 있었다. 또한 상세 입력 안내는 보류하고 다른 변경만 PR에 포함하도록 범위를 조정하여, 검토 중인 내용을 확정된 기능처럼 반영하는 일을 피할 수 있었다.
### 실패한 시도와 배운 점:
- 기존의 분석 성공 경험만으로 출시 준비가 끝났다고 생각하기 쉬웠다. 그러나 실제 배포에서는 동의 전 요청 차단, 다른 사용자의 기록 접근 방지, 신고 검토, 데이터 삭제까지 확인해야 했다. 테스트용 임시 계정을 만들어 실서버 검사 54개를 수행하고 운영자 화면의 저장 상태까지 확인하면서, 기능 구현과 실제 운영 검증은 별개의 단계라는 점을 배웠다.
- 휴대폰에서 정상 경로만 확인하지 않고, 분석 중 뒤로가기와 네트워크 단절도 직접 재현했다. 복구 후 자동으로 분석이 시작되지 않는지, 취소한 요청의 늦은 응답이 화면을 바꾸지 않는지, 글·사진과 수정한 문의 문장이 유지되는지 확인했다. 이를 통해 성공 결과뿐 아니라 사용자가 작업을 멈추거나 다시 시작하는 과정도 중요한 검증 대상임을 이해했다.
- 개인정보 처리 국가를 서울 DB 위치만 보고 판단하려 했지만, DB·인증과 운영 로그·지원 접근은 다른 위치에서 처리될 수 있다는 점을 확인했다. 공식 정책과 계정 설정을 함께 확인했고, Supabase에 구체적인 로그 국가와 보관기간을 문의했다. 받은 답변으로 DPA가 약관에 자동 포함된다는 사실은 확인했지만, 원래 질문한 로그 국가와 별도 내부 기록의 보관기간까지 답변된 것은 아니었다. 업체의 일반적인 준수 안내를 우리 서비스에 필요한 구체적인 사실 확인과 구분하는 법을 배웠다.
- 출시 일정이 빠듯해 Supabase를 다른 업체로 바꾸는 방안도 검토했다. AWS·네이버클라우드·NHN Cloud의 공개 자료와 비용을 비교했지만, 국내 업체나 유료 서비스라는 이유만으로 모든 개인정보 조건이 해결되는 것은 아니었다. DB 교체에는 임시 인증·권한·보관 및 삭제 기능의 재연결과 검증도 필요하므로, 가격과 기능뿐 아니라 이전 범위를 함께 판단해야 함을 배웠다.
### 남은 한계:
출시 대응 코드와 시험 서버 검증을 진행했지만 Google Play 공개 출시 완료로 기록하지 않았다. 최종 개인정보 문서와 실제 앱의 개별 동의 기록을 맞추고, 정책 URL과 서버 기능을 정식 활성화한 상태에서 최종 서명 AAB를 만들어 다시 검증해야 한다. 출시용 서명 키 생성과 테스트 앱 실행은 완료했지만, 최종 서명 파일 제작·심사 제출·공개는 별도로 확인할 항목이다.

Supabase의 EU 로그 저장 국가, 별도 내부 보안·지원 기록의 보관 및 삭제 기준은 추가 확인이 필요하다. 팀원이 별도로 내려받은 사용자 DB 백업의 존재 여부도 확인 대상으로 남아 있다. 확인된 사실만 문서에 반영하고, 미확정 항목과 실제 적용이 남은 부분을 팀원에게 구분해 전달할 예정이다. 무료 서버의 절전·첫 요청 지연과 임시 ID를 새로 만들었을 때 동일인을 판별하기 어려운 한계도 운영 시 계속 점검해야 한다.
