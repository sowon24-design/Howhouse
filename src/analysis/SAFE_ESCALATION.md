# 안전한 전문가 연결을 정상 결과로 처리 — 2026-11-01

## 원인과 변경

- 기존 프롬프트는 ‘위험하거나 확신할 수 없는 경우 unsafe/insufficient’로 종료하도록 넓게 지시했다. 원인을 단정할 수 없어도 안전한 점검 요청을 안내할 수 있는 경우까지 실패할 가능성이 있었다.
- 기존 A05의 안전 문구는 unsafe-input과 model-refusal 모두에 사용됐다. 당시 실제 모델 응답을 조회하지 않았으므로 특정 요청의 원인을 하나로 확정하지 않는다.
- 응답 검증의 실패는 api-error로 입력 화면에 안내되며, ‘정확히 4단계’ 조건 때문에 안전 A05가 뜨는 구조는 아니었다.
- 전문가 연락도 정상 해결 방법이다. 주의사항→가능한 안전한 확인·조치→적절한 연락 대상·전달 내용으로 구성한다. 위험한 확인은 생략하고 점검 요청으로 전환한다.
- 즉각 위험도 안전 확보·긴급 도움 요청을 안내할 수 있으면 정상 결과다. 일반 문자 회신을 기다리게 하거나 위험한 현장 조작·분해를 요구하지 않는다. 무조건 성공으로 바꾸거나 거절 응답을 조작하여 B02로 보내지는 않는다.

## 결과와 실패 계약

| 모델 decision | API/화면 |
| --- | --- |
| existing | 기존 사례 ID 그대로 B02·기존 문의 데이터 조회 |
| generated | 안전한 직접 대응 또는 전문가 점검 안내를 B02에 표시, 필요한 문의 문장을 B03에 제공 |
| insufficient | insufficient-input → A05 정보 부족 |
| unsupported | unsupported-input → A05 지원 범위 밖 |
| unsafe | unsafe-input → A05 안전한 대응 안내 자체가 어려움 |
| 제공사 refusal | model-refusal → A05 요청 안내 불가 |

기존 사례 우선·없고 정보가 충분할 때 생성 원칙은 유지한다. existing 원문을 다시 생성하지 않는다. App/전체 이동 계약은 유지한다. generated에는 아래 표시 필드를 추가했다. 새 실패 코드 unsupported-input은 서버 허용 목록, 앱 오류 타입·분류·HTTP 처리·A05 표시까지 연결했다.

## 생성 결과의 시간·책임·문의 문장

- `duration`: 안전한 조치의 예상 시간. 알 수 없으면 `-`. 건조·방문 대기와 실제 작업 시간을 혼동하지 않는다.
- `responsibility`: `집주인`, `세입자`, `-` 중 하나. 근거가 부족하면 `-`이며 원인·법적 책임을 단정하지 않는다.
- `reference`: 책임 주체가 표시되어도 반드시 판단 근거와 확인할 사항을 작성한다. B02의 기존 판단 참고 펼침 영역으로 전달한다.
- 생성 문의는 대상별 최대 4문장으로, 각 배열 항목에 한 문장을 담는다. 여러 문장이 한 항목에 들어오면 생성 결과 수신 시 문장 단위로 나눈다. 직접 수정한 본문이나 CSV를 다시 분리하지 않는다. 분리 후 4문장을 초과하면 응답 오류로 처리하며 자르지 않는다.
- `analysisVersion=analysis-v4-safe-escalation-facts-sentences`, 생성 계약 버전은 `2`다. `/session`으로 지원 버전을 확인하고 지원 서버에만 `X-Howhouse-Content-Version: 2`를 전송한다. 구형 앱에는 기존 형식으로 응답한다. 구형 서버의 결과를 받는 신형 앱은 시간·책임을 `-`로, 근거는 이전 버전에 제공되지 않았다는 안내로 표시한다.

관리실 등 적절한 연락 대상은 B02에 명시할 수 있다. B03은 현재 landlord/company 두 대상만 지원하며 새 관리실 탭을 만들지 않았다. 문의 메시지는 원인·책임·비용을 단정하지 않으며, 긴급 대응을 대신하거나 지연시키지 않는다.

## 단계 수

사용자가 기존 1~8단계 유지를 확정했다. generatedStepLimits를 프롬프트·응답 JSON Schema·서버 및 앱 공통 검증에 사용한다. 4개 고정·반복 단계 추가·필수 내용 생략을 요구하지 않는다. 문의 문장의 대상별 최대 4개 블록 제한은 해결 단계 수와 별개이며 변경하지 않았다.

B02/StepCards 원본은 변경하지 않았다. 실제 steps 배열 길이로 카드·진행 표시·첫/마지막 화살표를 처리한다.

## 검증과 한계

- 무료 자동 검사 109개 통과: 안전한 전문가 연결 응답, HTTP 200 및 B02/B03 표시 변환, 1·2·3·5·8단계 유지, 0·9단계 거절, 실패 세 사유의 HTTP 422 전달, 제공사 거절 유지, 기존 사례 원문 유지, 자동 재시도 없음.
- 임시 로컬 페이지에서 실제 B02/B03 컴포넌트로 1·2·5·8단계를 조작했다. 각 마지막 n/n 표시·활성 진행 수 n·다음 비활성·카드 X=24px 정렬 확인. 1단계는 양쪽 화살표 비활성. 집주인/업체 문의 본문과 A05 다섯 사유별 문구도 확인했다. 검증 페이지는 작업 후 삭제했다.
- 모의 모델 응답을 사용했으며 실제 OpenAI 호출은 0회다. 프롬프트 변경에 따른 실제 모델 판단 품질·Android 실기기 동작을 검증한 것은 아니다.
- 평가용 professional-gas/professional-door 기대값도 안전한 전문가 안내를 정상 결과로 보도록 수정했다. 정상 결과를 기대했는데 의미상 분석 실패가 온 경우 평가 failed로 집계한다. 서버·통신 장애 blocked와 구분한다.
- 일반적인 안전 원칙 참고: [한국가스안전공사](https://www.kgs.or.kr/), [시설 이상 시 가스공급자에 수리 요청 안내](https://www.kgs.or.kr/kgs/abbc/view.do). 실제 사례의 안전·정확성을 이 테스트로 보증하지 않는다.

## 실제 반영 시

1. 변경 내용을 소원·예슬이 확인한 뒤 서버 재시작 또는 호스팅 서버 재배포, 앱 재빌드/동기화가 필요하다. 현재 실행 중인 외부 서버·설치 APK는 자동으로 바뀌지 않는다.
2. analysisVersion과 프롬프트 해시가 바뀌어 이전 버전의 저장 답변은 새 요청에서 재사용되지 않는다. 파일·DB 삭제나 개발 호출 한도 초기화는 하지 않았다.
3. 승인된 시험 환경에서 기존 사례 1개, 전문가 연결 1개, 정보 부족/지원 밖 사례를 구분해 실제 검증한다. 무료 모의 검사와 실제 API 성공을 구분한다.
4. 초기 안전 변경 검증 당시 실제 유료 분석 호출은 하지 않았다. 이후 배포 진행 상태는 아래를 따른다. 약관·Notion은 이번 분석 변경 범위가 아니다.
