# 로그인 후속 도입 검토 — PR62 v9

2026-11-12. 검토만 수행. 로그인 UI·인증 공급자·SMTP·리디렉션·운영 설정은 변경하지 않았다.

## 결론

AI·사진 분석·Supabase Free 구조를 유지하면서 정식 로그인을 나중에 추가할 수 있다. 현재 앱은 익명 인증만 구현되어 있으므로 지금 로그인 기능이 완성되었다는 뜻은 아니다. 현재 출시 작업에 로그인 추가를 새 필수 조건으로 넣지 않는다.

## 현재 코드에서 확인한 것

- `src/analysis/app-session.ts`: 익명 signup과 refresh, 로컬 세션 보관·초기화가 있다. 이메일·OAuth 로그인, 계정 연결·전환·로그아웃 화면은 없다.
- `server/analysis/trial-access.mjs`: Auth `/user`로 확인한 익명 사용자와 이메일 인증 완료 사용자를 허용한다. `app_metadata`에 있는 별도 권한만 검토자 권한으로 인정한다. 로그인 사용자라는 이유로 검토자 권한을 부여하지 않는다.
- `server/analysis/release-data.sql`과 `release-store.mjs`: 기록은 Auth 사용자 ID별로 연결된다. 90일 미활동 자동 삭제 대상을 익명 사용자로 한정하며 실행 전에도 다시 확인한다. 정식 계정의 탈퇴·보관 기준은 별도로 설계·고지해야 한다.
- 동의·삭제 코드·삭제 대기 영수증 등 일부 로컬 키는 서버 주소 기준이다. 로그인 도입 시 사용자별로 분리하거나 계정 전환 때 초기화·재조회해야 한다. 단순히 새 토큰만 교체하면 계정 A의 로컬 표시가 B에게 남을 수 있다.
- 답변·의견 암호화에는 소유자 ID가 연관된다. 기존 계정으로 로그인하면서 익명 자료의 owner_id만 임의 변경하거나 동의 이력을 합치는 방식은 사용하지 않는다.

## 권장 구현 순서

1. 현재 익명 이용을 유지하고 원하는 이용자만 계정을 연결하도록 한다. 가능하면 같은 Auth ID를 유지하는 익명→정식 계정 연결을 사용하여 기존 기록·증빙 연결을 보존한다.
2. 새 계정 연결과 이미 존재하는 계정 로그인은 구분한다. 기존 계정 로그인은 서로 다른 ID이므로 우선 기록을 자동 병합하지 않는 편이 단순하다. 이전을 제공할 때는 양쪽 계정 소유 확인, 암호화 자료 재처리와 이력 보존 정책이 필요하다.
3. 세션 교체·로그아웃 때 진행 중 요청 취소, 결과/평가/동의/삭제 코드 초기화, 서버 동의 재조회, 타 계정 자료 노출 방지를 구현한다. 로그인만으로 AI 동의를 받은 것으로 처리하지 않는다.
4. Android OAuth·메일 링크의 앱 복귀(검증된 리디렉션, PKCE 등), 이메일 인증·복구 또는 소셜 연결 실패·취소를 검증한다. 공급자 비밀키는 앱에 넣지 않는다.
5. 추가되는 이메일·외부 계정 ID 등 실제 수집 항목·목적·기간·탈퇴 절차·위탁/국외 처리 안내를 수정한다. 현재 '실명 가입이나 이메일·비밀번호 입력을 요구하지 않음'이라는 v9 문구를 정식 로그인 출시 시 그대로 사용하지 않는다. 로그인 이메일을 OpenAI 입력에 추가할 필요는 없다.
6. A/B 계정 전환·다른 기기 복구·연결 실패·동의 거부/철회·삭제 후 세션 거절을 시험한다.

## 무료 유지와 선택지

Supabase Free를 사용한다는 이유만으로 로그인 기능이 금지되는 것은 아니다. 하지만 이메일 OTP·인증·복구를 기본 발송 서비스만으로 일반 이용자에게 제공할 수 있다고 전제하면 안 된다. 공식 문서는 기본 SMTP를 비운영용으로 설명하고 조직 팀 주소로 제한하며 현재 시간당 2건 제한을 안내한다. 이메일 방식은 적합한 외부 SMTP와 발신 설정·무료 한도 확인이 필요하다. 여기서 가입하거나 설정하지 않았다.

소셜 로그인은 이메일 발송 의존성을 줄일 수 있으나 제공자 계정 설정·동의 항목·추가 처리업체/국가 안내가 필요하다. 현재 공급자 활성화 여부·심사·한도·운영 비용을 확인하지 않았으므로 특정 방식이 즉시 무료 운영 가능하다고 보증하지 않는다. 구체 방식은 로그인 도입을 요청할 때 결정하면 된다.
