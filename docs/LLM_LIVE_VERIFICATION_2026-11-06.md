# 어쩌집 실서버 검증 결과

검증일: 2026-11-06 (한국 시간). 대상: 기존 Render 시험 서버 `howhouse-analysis-test.onrender.com`, 실행 코드 `6df4b36`. Supabase는 기존 서울 프로젝트를 사용했다.

## 통과한 범위

- 실제 HTTPS 서버·Supabase 인증·저장을 통과하는 검사 **54개 통과**. 상세 결과는 [검사 목록](verification/llm-live-2026-11-06.json)에 있다. 유료 AI 분석은 **0회**이며 사용자 글·사진을 보내지 않았다.
- 동의 전 분석 차단, 미완성 동의 거절, 테스트 동의 저장, 철회 후 차단을 확인했다. 동의 후 잘못된 요청도 분석 단계로 넘기지 않았다.
- 기존 사례와 생성 결과 식별값 각각에 대해 좋아요→싫어요→해제, 이전 선택의 뒤늦은 도착 차단, 동일 요청 중복 방지, 변경된 내용의 동일 요청 번호 거절을 확인했다.
- 의견 저장·동일 제출 재시도·공백/여러 사유 거절, 잘못된 사례와 등록되지 않은 생성 결과 거절을 확인했다.
- 다른 임시 계정의 평가 분리, 생성 결과 권한 분리, 일반 사용자의 운영자 접근 및 DB 직접 읽기 차단을 확인했다.
- 실제 운영자 화면에서 테스트 신고 2건을 불러오고 기존 사례는 `needs-change`, 생성 결과는 `reviewed`로 저장한 뒤 재조회로 확인했다.
- 앱 경로의 본인 삭제와 외부 삭제 코드 경로가 모두 성공했다. 삭제 영수증 재확인, 잘못된 영수증 거절, Supabase 인증 계정 삭제까지 확인했다.
- 중간 종료된 검사 계정 2개는 사용자 승인 후 정확한 테스트 표시·계정 ID를 확인해 삭제 대기에 넣었다. 실제 서버 작업자가 인증 계정까지 정리했다.
- DB에서 이번 검사의 총 4개 계정을 기준으로 인증 계정·동의 식별·결과·평가·의견·중복 식별·운영자 검토·답변·호출·삭제 대기 **10개 조회가 전부 0건**임을 확인했다. 기존 운영자·팀원 계정은 삭제 대상이 아니었다.

## 검증 방식과 범위의 한계

- 생성 결과 저장 검사는 별도의 유료 생성 없이, 해당 테스트 계정에만 등록한 합성 결과 식별값으로 진행했다. 실제 모델이 새 해결책을 생성하는 품질 검사와 구분한다.
- 원본 사용자 문제·사진·전화번호·개인 메시지는 테스트 데이터에 포함하지 않았다. 인증 토큰과 삭제 코드는 검사 프로세스 메모리에서만 사용했고 결과 파일에 쓰지 않았다.
- 첫 검사 도구의 대기 입력이 종료되는 문제가 있어 입력 연결을 유지하도록 수정한 뒤 54개 검사를 다시 완료했다. 중단 때 생성된 두 계정도 정리했다.
- DB 전체 장애나 실제 제공업체 장애를 고의로 만들지 않았다. 저장 장애·취소 경합·90초 제한 등 기존 자동 검사와 Android 검사 결과를 이번 실서버 54개 검사와 혼동하지 않는다.
- 7일·30일·90일·365일을 실제로 기다린 장기 관찰 결과는 아니다. 보관 SQL·권한 검사 및 이번 삭제 작업자의 실제 처리 결과를 구분한다.

## 종료 설정

검증 중 `RELEASE_DATA_ENABLED=1`로 새 기능을 임시 활성화했다. 기존 시험 앱에는 아직 최종 동의 흐름이 없으므로 종료 후 `0`으로 되돌렸다. 최종 복원 배포 `dep-dbmpn7ijnfac73b5du6g`가 Live인 것과 실제 개인정보 경로의 `503 release-not-configured` 응답을 확인했다. 미국 처리 설정은 `us`를 유지했고 공개 health는 `ok`였다. 공개 정책 준비 플래그는 켜지 않았다. 최종 고지·호환 앱 배포 후 동의·철회·삭제 기능을 상시 활성화해야 한다. 운영자 검증 세션은 로그아웃했다.
