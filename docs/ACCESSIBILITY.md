# 어쩌집 접근성 점검 가이드 · 워크숍

작성일: 2026-11-10

이 문서는 수업의 **사용자 제약 상황 정의 → 문제 분석 → 개선 방향 선정 → 개선 전후 비교 → 발표·성찰** 흐름을 어쩌집에 적용한 검사 기준이다. Figma 시안, React 웹, Android WebView를 구분해서 검사한다. 이 문서는 검사 기준이며, 실제 수행한 검토·개선 결과는 [접근성 리포트](ACCESSIBILITY_REPORT.md)에 기록한다.

## 1. 목표와 기준 문서

집에 문제가 생겼을 때 시각·운동·청각·인지 또는 환경의 제약 때문에 안내를 읽거나 다음 행동을 선택하지 못하는 상황을 줄인다. 직접 수리뿐 아니라 집주인·전문 업체에 도움을 요청하는 과정도 포함한다.

- 웹 콘텐츠의 평가 목표: **WCAG 2.2 A·AA**. 아래 표는 핵심 항목을 추린 것이며 전체 준수 판정표를 대신하지 않는다.
- Android 조작: Google의 터치 영역·TalkBack 검사 지침을 함께 사용한다.
- 사용자 상황 정의: Microsoft Inclusive Design의 영구적·일시적·상황적 제약 관점을 활용한다.
- 제품 기준: [W9 PRD](PRD_w9%20수정안.md), [화면별 기능정의](화면별_기능정의.md), [DESIGN.md](../DESIGN.md), [컴포넌트 계약](../src/components/CONTRACT.md), [UX 라이팅](UX_WRITING.md).
- 시안은 사용자가 지정한 최신 출시용 Figma를 확인한다. 오래된 기능정의와 최신 합의가 다르면 차이를 기록하고, 검사자가 임의로 제품 동작을 확정하지 않는다.

접근성 개선이 기존 색상·모션·스크롤 규칙과 충돌하면 **측정 결과와 개선안**을 먼저 제시한다. 이 문서만을 근거로 공통 토큰이나 화면을 자동 변경하지 않는다.

## 2. 워크숍 대상 사용자와 해결할 상황

### 대표 페르소나 — 워크숍용 가설

혼자 사는 24세 대학생 ‘민서’. 손목 부상으로 한 손만 사용하고, 작은 글씨는 확대해서 읽는다. 집의 문제를 발견했지만 수리 용어에 익숙하지 않아 무엇부터 해야 할지 막막하다. 이는 실제 인터뷰 결과가 아닌 **검사용 가상 사용자**다.

**목표:** 문제를 입력하거나 기존 사례를 찾아, 해결 단계를 읽고 필요하면 문의 메시지를 수정·복사할 수 있다. 작은 아이콘의 정밀한 터치나 드래그, 색 구분에만 의존하지 않아야 한다.

| 제약·상황 | 겪을 수 있는 어려움 | 점검할 해결 목표 |
| --- | --- | --- |
| 손목 부상·한 손 사용 | 작은 X·사진 삭제·평가 아이콘 오조작, 시트 드래그 어려움 | 넓고 겹치지 않는 터치 영역, 드래그 외 닫기 방법 |
| 저시력·큰 글씨 사용 | 약관·오류·보조 문구가 흐리거나 확대 시 잘림 | 충분한 대비, 확대·줄바꿈, 가려지지 않는 CTA |
| 시각 정보 없이 TalkBack 사용 | 아이콘 용도, 체크 상태, 분석 완료를 알기 어려움 | 이름·역할·상태 전달, 읽기 순서와 초점 이동 |
| 청각 제약·소리를 켤 수 없는 환경 | 외부 영상 설명을 듣지 못함 | 핵심 해결 안내를 앱의 글로도 이해 가능 |
| 수리 경험 부족·불안한 상황 | 전문 용어, 모호한 오류, 실패 후 행동을 이해하기 어려움 | 쉬운 말, 원인에 맞는 다음 행동, 입력 보존 안내 |
| 움직임에 민감한 사용자 | 반복 일러스트·시트 이동·탄성 스크롤이 불편 | 동작 줄이기 설정에서 불필요한 움직임 억제 |

대표 페르소나 하나로 모든 장애를 설명하지 않는다. TalkBack·청각·움직임 제약은 별도 검사 조건으로 다룬다. 시뮬레이션은 실제 당사자의 사용 경험을 대체하지 않는다.

## 3. 우선 검사할 사용자 흐름

워크숍 발표는 다음 중 **한 흐름과 핵심 문제 2~3개**에 집중하고, 확장 검사는 나머지 화면에 적용한다.

1. **기존 사례:** A01 홈 → B01 카테고리 → B02 해결 방법 → 문의 시트 → B03 수정·복사.
2. **문제 분석:** A02 글·사진 입력 → 필요한 동의 → A04 대기 → A06 문제 확인 → B02 → B03.
3. **오류 복구:** A05 실패·A07 이용 제한·F02 단절 → 안내 확인 → 정해진 복귀 경로. 입력 보존·초기화와 자동 재분석 금지도 확인.
4. **시작·정보 관리:** E01~E04 소개·동의·닉네임 → 홈, D01 및 개인정보 관리·철회·삭제 경로.

유료 API 없이 샘플 성공·실패로 우선 검사한다. 샘플 통과를 실제 서버 성공으로 기록하지 않는다. 동의 저장·의견 제출·삭제 등 서버 검사는 별도 승인된 테스트 데이터로만 수행한다.

### 모션과 바텀시트 추가 기준

- 자동 반복 모션이 5초를 넘고 다른 콘텐츠와 함께 표시되면 일시정지·정지·숨김 필요 여부를 WCAG 2.2.2 A에 따라 검사한다. 번쩍임은 2.3.1 A를 확인한다.
- `prefers-reduced-motion`에서 장식 모션·탄성 이동을 줄이는 것을 프로젝트 검사 항목으로 둔다. 상호작용 애니메이션 억제 자체는 WCAG 2.3.3 **AAA**이므로 AA 필수 항목과 구분한다.
- 모달 시트가 열리면 초점이 내부로 이동하고, 배경은 스크롤뿐 아니라 키보드·TalkBack 탐색에서도 비활성인지 검사한다. 닫으면 호출 버튼으로 초점이 돌아와야 한다.
- 2단 시트는 최상단만 조작 가능해야 한다. 닫기·Escape·Android Back의 단계별 복귀를 확인한다. Android에서 키보드가 먼저 닫히는 조건도 구분한다.
- 시트 제목·닫기 버튼을 읽을 수 있어야 하며 손잡이 드래그가 유일한 종료 수단이 되어서는 안 된다. 관련 구현 참고: [WAI-ARIA 모달 패턴](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).
- 기존 ‘본문 스크롤 금지’·‘CTA 고정’ 규칙 때문에 큰 글씨에서 잘리면 접근성 이슈로 기록한다. 필요한 예외 스크롤·레이아웃 개선은 사용자와 합의 후 적용한다.

## 6. 검사 실행 순서와 도구

### 준비

1. 브랜치·커밋, 검사 날짜, 웹/시험 APK, Android·WebView·TalkBack 버전, 기기, 화면 크기, 글자 배율, 샘플/API 모드를 기록한다.
2. 현재 디자인·계약·화면별 요구를 확인하고 위 흐름 중 하나를 선택한다. 개인정보 없는 샘플 문장·사진을 사용한다.
3. 기본 상태 외에 오류·선택·로딩·시트·큰 글씨 상태를 준비한다. 화면 ID만으로 상태가 같은 것으로 간주하지 않는다.

### Figma 시안 검사

- Contrast Checker, Stark, A11y 등 수업에서 소개한 도구로 실제 글자/배경 쌍을 측정한다. 도구명·버전과 측정 대상을 기록한다.
- 폰트 크기·굵기, 터치 영역 설계, 색 외 상태 표시, 문장·아이콘 의미를 확인한다.
- Figma 결과는 시각 설계 근거다. DOM 라벨·키보드 초점·TalkBack 통과 근거로 쓰지 않는다.

### 실행 웹 검사

- 프로젝트 루트에서 `npm run dev -- --strictPort`로 실행하고 터미널에 표시된 주소를 연다. 핵심 흐름을 실제로 조작해 각 상태를 만든다.
- **WAVE 브라우저 확장** 등으로 열린 로컬 페이지를 검사한다. WAVE 웹사이트의 URL 입력란으로 다른 컴퓨터의 localhost를 검사할 수 있다고 가정하지 않는다. [WAVE 공식 안내](https://wave.webaim.org/)
- 자동 검사로 라벨·대비·구조 문제 후보를 수집한 뒤 사람이 재현한다. 추가 검사 도구 설치는 이번 문서 작성에 포함하지 않는다.
- 마우스 없이 키보드 탐색, 200% 글자 확대, 320 CSS px 상당 너비, 가로 화면, 텍스트 간격 변경, 동작 줄이기를 수동 검사한다.
- 코드에서는 의미 있는 HTML, `label`, `alt`, `aria-*`, 초점 복원, 상태 알림, 고정 높이·overflow를 살핀다. 속성이 존재하는 것만으로 통과 처리하지 않는다.

### Android 실기기 검사

- 동일 빌드에서 TalkBack으로 이름·역할·순서·상태를 듣고, 시트 안팎·화면 이동·오류 복구를 수행한다.
- 글꼴·표시 크기를 키워 입력·키보드·CTA·약관·긴 결과를 확인한다. WebView가 시스템 글꼴 배율을 실제 반영하는지도 기록한다.
- Accessibility Scanner로 터치 크기·대비 등의 후보를 찾고 직접 조작해 검증한다. 외부 키보드·Switch Access 검사는 사용 가능한 환경에서 추가한다.
- 에뮬레이터 결과와 실기기 결과는 분리한다. Android 공식 지침은 자동 분석·수동 검사·사용자 테스트를 함께 권장한다. [Android 접근성 테스트](https://developer.android.com/guide/topics/ui/accessibility/testing)

자동 검사에서 오류가 없다는 것은 전체 접근성 통과가 아니다. **미검증 항목은 통과로 집계하지 않는다.**

## 7. 개선 리포트 작성 양식

결과는 별도의 `docs/ACCESSIBILITY_REPORT.md`에 작성한다. 이 문서는 기준, 리포트는 실제 근거를 보관하는 용도다. 완료한 워크숍 결과는 해당 리포트를 참고한다.

### 검사 환경·범위

- 검사일 / 검사자 / 커밋·APK 버전:
- 선택한 사용자·상황 / 흐름 / 화면·상태:
- 기기·OS·WebView·브라우저·TalkBack / 화면 크기·배율:
- 도구·버전 / 샘플·실서버 구분:
- 제외 범위와 이유:

### 발견 사항 표

| ID | 화면·상태 | 사용자에게 생기는 문제 | 근거·측정값·기준 | 개선안 | 우선순위 | 상태 | 개선 후 재검증 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| A11Y-001 | 검사 후 작성 | 검사 후 작성 | 캡처·재현 순서·기준 번호 | 검토 후 작성 | 판정 전 | 미검증 | 미실시 |

- 우선순위: **높음** 핵심 흐름 진행 불가·정보 접근 불가 / **중간** 큰 어려움·오조작 유발 / **낮음** 진행 가능하나 이해·편의 개선 필요. 이는 프로젝트 우선순위이며 WCAG A·AA 등급과 다르다.
- 상태: 미검증 / 통과 / 실패 / 해당 없음(사유 필수) / 보류(차단 원인 필수).
- 각 이슈에 재현 순서, 기대 동작, 실제 동작, 담당 영역을 적는다. 시안만으로 발견한 문제와 실행 환경에서 재현한 문제를 구분한다.
- 개선 전후를 동일 기기·배율·화면 상태로 캡처한다. 대비 수치·터치 영역·초점 이동은 비교 가능한 근거를 남긴다.
- 캡처는 `docs/assets/accessibility/` 아래 보관하고 개인정보·토큰·실제 문의 내용은 제외한다. 아직 측정하지 않은 수치나 사용자 반응을 만들어 넣지 않는다.
- 전체 이슈 수뿐 아니라 핵심 과업 완료 여부, 오조작, 재시도, 미검증 범위를 요약한다. 개선 후 회귀 검사를 통과해야 해결로 기록한다.

## 8. 워크숍 발표·성찰

**발표 슬라이드 2~3장**

1. 사용자·제약 상황·핵심 흐름과 개선 전 문제. 누가 어떤 행동에서 막혔는지 설명.
2. 개선 전후 화면을 나란히 배치하고 텍스트·색·버튼·초점·피드백에서 바꾼 점과 근거 제시.
3. 재검증 결과, 여전히 남은 제약, 적용 범위와 다음 확인. 어떤 사용자에게 도움이 되었는지 설명.

**성찰 3문장 작성 틀**

- 처음에는 ___을 당연하게 생각했지만, ___ 상황에서 ___이 어려워짐을 확인했다.
- ___을 개선한 뒤 ___ 검사에서 ___을 확인했다. 아직 확인하지 못한 부분은 ___이다.
- 다음에는 ___ 사용자의 의견 또는 ___ 환경의 테스트를 통해 ___을 보완하겠다.

실제 검사 전에는 빈칸을 경험한 사실처럼 채우지 않는다. 도구가 발견한 문제, 사람이 판단한 문제, 사용자 의견을 구분한다.

## 9. AI에게 검사 요청할 때

> `docs/ACCESSIBILITY.md`와 최신 디자인·컴포넌트 계약·화면 동작을 읽고, 먼저 현재 브랜치와 변경사항을 보존해 주세요. 선택한 흐름을 Figma 시각 검사, 웹 자동·수동 검사, Android 실기기 검사로 나눠 점검해 주세요. 실행 가능한 범위만 검사하고 실제 측정·재현 근거를 기록해 주세요. 확인할 수 없는 항목은 미검증으로 남기고, 통과나 사용자 경험을 추정하지 마세요. 결과와 우선순위·개선안을 `docs/ACCESSIBILITY_REPORT.md`에 작성해 주세요. 기존 디자인과 충돌하는 개선, 팀원 담당 파일 변경은 적용 전에 알려 주세요. 이번에는 UI 수정·패키지 설치·유료 API 호출·서버 데이터 변경·commit·push를 하지 마세요.

## 10. 참고 자료

자료 확인일: 2026-11-10. 기업 지침과 구현 예시는 WCAG 규범과 구분한다.

- [W3C WCAG 2.2](https://www.w3.org/TR/WCAG22/): 국제 웹 접근성 기준. 위 기준 번호의 원문.
- [W3C ARIA Authoring Practices — Modal Dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/): 시트·대화상자 의미와 초점 구현 참고.
- [Google Android 접근성 원칙](https://developer.android.com/guide/topics/ui/accessibility/principles): Android 접근성 설계 참고.
- [Google 터치 영역](https://support.google.com/accessibility/android/answer/7101858): 그림 크기와 터치 영역, 48dp 권장.
- [Google Android 접근성 테스트](https://developer.android.com/guide/topics/ui/accessibility/testing): TalkBack 등 실행 환경 검사.
- [Microsoft Inclusive Design — Inclusive 101](https://inclusive.microsoft.design/articles/inclusive-101-guidebook): 사용자 제약과 배제 상황을 정의하는 관점.
- [WAVE](https://wave.webaim.org/): 자동 문제 탐지와 사람의 평가를 지원하는 검사 도구.
- 사용자 제공 수업자료: ‘우리 서비스 UI 디자인 접근성 테스트하기’, ‘Inclusive UI Redesign’. 워크숍 순서와 산출물의 기준.
